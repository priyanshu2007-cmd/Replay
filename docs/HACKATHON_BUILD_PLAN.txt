Overview
Replay turns a screen recording of a web-app bug into a reproducing Playwright test and a
verified fix, in about 60 seconds. It enters Track A (Coding and Agentic Engineering) and
the submission is due Oct 30, 2026, 10:30 PM IST.
The pitch: QA testers and users report bugs as videos ("it broke when I did this").
Developers then spend 30–90 minutes reproducing the bug before they can even start
fixing it. Replay does the reproduction for them, and proves it with a test.
The 30-second wow moment: drag in a 20-second bug video. The UI scrubs to the exact
frame where it breaks, highlights the guilty file, shows a red failing test, then a patch, then
the same test going green.
Scope rule: Replay never claims a fix works unless a real test run says so. Every result
shown is from an actual execution in a sandbox.
Definition of done for the hackathon: 4 planted bugs in a demo app reproduced and fixed
end-to-end (target ≥ 3 of 4 green on a live run), one honest attempt on a real open-source
app with its success rate shown, public URL, public repo, ≤ 3-minute video.

System architecture
The browser uploads the video straight to Supabase Storage, the API queues a run in
Supabase Postgres, and the worker drives the seven stages, calling Nemotron models on
Token Factory and running tests in the sandbox.
End-to-end flow
1. Browser requests a presigned URL and uploads the video to Supabase Storage (or
picks a sample).
2. POST /api/runs  creates a queued run; the browser opens the SSE stream for that run.
3. Worker claims the run, extracts frames with ffmpeg and stores them.
4. Watch: Super VL reads the frames → BugReport  (steps, failure frame, expected vs
actual).
5. Locate: Lightning reads the packed repo + BugReport → ranked suspects and
selectors.
6. Reproduce: Ultra writes a Playwright test and runs it in the sandbox until it fails for the
right reason.
7. Verify: Super VL compares the test screenshot with the failure frame.

Agents
Replay is a pipeline of five agents plus deterministic gates, not a free-form multi-agent
chat. Each agent has one job, one model, a fixed set of tools and a Zod-validated JSON
output. A step only advances when its gate passes.

Deterministic gates (no AI)
1. Repro gate: the test must fail with an assertion error, not a timeout, selector-not-found
or syntax error. Otherwise the Reproducer retries (max 4).
2. Same-symptom check: the failing test's final screenshot and the video's failure frame
are sent to Super VL with one question: "Do these show the same defect? yes/no +
reason." This is the side-by-side evidence card in the UI.
3. Fix gate: the repro test must pass and the existing test suite must still pass. Otherwise
the Fixer retries (max 3).

Prompts
Every agent gets a short system prompt with: its single job, the exact output schema, the
rules it must not break, and what to do when unsure. Keep temperature low (0.1–0.2) and
always request JSON. Store prompts as versioned files in packages/agents/prompts/  so
you can show them in the README.
1. Watcher (Super VL)
You are the Watcher in Replay, a system that reproduces web-app bugs from 
screen recordings.
You receive frames from a screen recording, each labelled with its timestamp 
in seconds, plus an optional note from the reporter.
Your job: describe exactly what the user did and where the app misbehaved.
Rules:
- Only describe what is visible in the frames. Never guess at code or causes.
- List user actions in order, each with the timestamp of the frame where it 
happens.
- Quote on-screen text exactly (button labels, error messages, values).
- Identify the single frame where the defect is first visible.
- If you need a closer look at a time range, call get_frames.
- If no defect is visible, set defect_found to false.
Return only JSON matching this schema:
{
  "defect_found": boolean,
  "summary": string,                // one sentence, e.g. "Cart total shows 
NaN after clearing quantity"
  "steps": [{"t": number, "action": string, "target": string, "value": 
string|null}],
  "failure_frame_t": number,
  "expected": string,
  "actual": string,
  "visible_text": string[],
  "page_url_or_route": string|null,
  "confidence": number              // 0 to 1
}

2. Locator (Lightning)
You are the Locator in Replay. You receive the full source of a web app 
(packed as files with paths and line numbers) and a BugReport produced from a 
screen recording.
Your job: find the code most likely responsible for the defect.
Rules:
- Trace from the UI the user touched (labels and text in the BugReport) to 
the components, handlers and state logic involved.
- Rank at most 5 suspects. Each must point to a real file and line range from 
the source you were given.
- Explain each suspect in one sentence that links the code to the visible 
symptom.
- Never invent files, functions or line numbers. Use search_code or read_file 
to confirm.
Return only JSON:

3. Reproducer (Ultra)
You are the Reproducer in Replay. You receive a BugReport (what the video 
shows), the Locator's suspects and selectors, and tools to read code, write a 
Playwright test and run it.
Your job: write ONE Playwright test (TypeScript, @playwright/test) that fails 
because of the same defect the video shows.
Rules:
- Follow the user's steps from the BugReport in order.
- Prefer getByRole, getByLabel and getByTestId over CSS selectors.
- End with an assertion that encodes the EXPECTED behaviour, so it fails on 
the current code.
- Base URL is http://localhost:5173. Do not use external network.
- After writing, call run_test. A valid reproduction fails with an assertion 
error that matches the BugReport's "actual" behaviour.
- If the test fails for another reason (timeout, selector not found, syntax), 
read the error, fix the test and run again.
- Never weaken the assertion just to make the run look right.
- You have at most 4 runs.
When done, return only JSON:
{"status": "reproduced" | "not_reproduced", "test_name": string, "assertion": 
string, "failure_message": string, "notes": string}

4. Fixer (Ultra)
You are the Fixer in Replay. You receive the BugReport, the suspects, a 
failing reproduction test and its failure output, and tools to read files, 
apply a patch and run tests.
Your job: make the smallest correct change to the application code so the 
reproduction test passes and the existing tests still pass.
Rules:
- Change application code only. Never edit tests, Playwright config or 
package files.
- Produce a unified diff and apply it with apply_patch.
- Fix the root cause, not the symptom (e.g. parse input to a number; do not 
hide NaN with a string replace).
- After each patch, call run_test on the reproduction test, then run_suite.
- If something fails, read the output and revise. You have at most 3 patch 
attempts.
When done, return only JSON:
{"status": "fixed" | "not_fixed", "diff": string, "root_cause": string, 
"files_changed": string[], "risk": "low" | "medium" | "high"}

Return only JSON: {"same_defect": boolean, "reason": string}

Prompt guide
Use this guide to write, test and fix every agent prompt yourself, with help from any AI
assistant. A good agent prompt is not clever wording. It is a precise contract: inputs, one
job, rules, tools, output schema and what to do when unsure. Then it is tested against your
sample bugs and changed one thing at a time.
The 7-part skeleton for every agent prompt
1. Role: one line. "You are the Locator in Replay, a system that reproduces web-app bugs
from screen recordings."
2. Inputs: exactly what the agent receives and in what format (frames with timestamps,
packed repo, BugReport JSON).
3. Job: one sentence, one outcome. If you need "and", it might be two agents.
4. Rules: 4–8 short bullets. Include the failure you fear most ("Never invent file paths",
"Never weaken the assertion").
5. Tools: when to call each tool and the limit ("at most 4 runs").
6. Output: the exact JSON schema with types and one-line comments. Say "Return only
JSON."
7. When unsure: what to return instead of guessing ( defect_found: false , status:
"not_reproduced" , a confidence  field).

Tool-calling loop (Reproducer and Fixer)
async function runAgent({ model, system, user, tools, handlers, maxTurns, 
emit }) {
  const messages = [{ role: "system", content: system }, { role: "user", 
content: user }];
  for (let turn = 0; turn < maxTurns; turn++) {
    const t0 = Date.now();
    const res = await nebius.chat.completions.create({ model, messages, 
tools, temperature: 0.2 });
    const msg = res.choices[0].message;
    messages.push(msg);
    await emit({ type: "llm", model, usage: res.usage, ms: Date.now() - t0 
});
    if (!msg.tool_calls?.length) return msg.content;          // final JSON 
answer
    for (const call of msg.tool_calls) {
      const args = JSON.parse(call.function.arguments);
      const result = await handlers[call.function.name](args);  // e.g. 
run_test in Docker
      await emit({ type: "tool", name: call.function.name, args, result });
      messages.push({ role: "tool", tool_call_id: call.id, content: 
JSON.stringify(result) });
    }
  }
  throw new Error("max turns reached");
}
Every emit  writes a row to run_events  and pushes it to the browser over SSE, so the
judges watch each model call, tool call, token count and latency live.

Backend design
The backend is two processes from one codebase: an API that accepts runs and streams

API endpoints (Hono)
Worker loop
1. Poll: UPDATE runs SET status='running', locked_at=now() WHERE id = (SELECT

Database and storage
Use one free Supabase project for both the database (Postgres) and file storage. It lives
outside your backend host, so stored runs stay viewable in replay mode even when the
VM or laptop is off. Postgres holds runs, events and metrics; Supabase Storage holds
videos, frames, screenshots and traces, and Postgres keeps only their keys.
Connect the worker and API with the Postgres connection string ( DATABASE_URL , use
the pooler URL) through Drizzle, exactly as before.
The frontend reads finished sample runs directly with @supabase/supabase-js  and
the anon key, protected by Row Level Security: only rows with is_sample = true  or a
share token are readable.
Free projects pause after a period of inactivity, so add a weekly GitHub Actions
workflow that runs a tiny query to keep it awake through judging.
Local development: run Postgres in Docker ( postgres:16 ) and point DATABASE_URL  at
it; switch to Supabase for the deployed demo.
